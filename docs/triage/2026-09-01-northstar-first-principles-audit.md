## Executive assessment

Northstar's core is sound and genuinely differentiated: a docs spine with one
authority chain, ready-card execution grammar, and a file-based
orchestrator/worker/PR loop that demonstrably runs real multi-lane work. The
problem is what has accreted around that core. The repository now carries
roughly 47,000 lines of Markdown, of which 27,800 (59%) is `docs/` — Northstar
planning Northstar. The g02 roadmap is 43 milestones, and the large majority
improve Northstar's own process rather than a consumer-visible capability.
Validation has drifted from "check structure" to "assert prose": ~5,200 lines
of Rhai checkers, including one data file hardcoding 167 required file paths
and hundreds of substring assertions on doctrine wording. `PAPERCUTS.md` is
the clearest witness: most open entries are friction generated by Northstar's
own checkers, evidence harnesses, and oracles, not by the docs system they
guard.

The single largest strategic ambiguity is the language-quality packs
(Rust/TypeScript). They are impressive engineering with real evidence
discipline, but they are a different product than a docs spine, they generated
a disproportionate share of papercuts and roadmap effort, and their connection
to "operators run agent projects with less babysitting" is indirect.

All adoption evidence is operator-owned dogfood (Signal, Poodle, Figmatic,
Jetstream, Acowtancy, Swallowtail, T3 Code, Bovine — all the same operator's
projects). That is honest and repeatedly acknowledged in the docs, but it means
every "reusable across projects" claim is proven only for one user's taste and
toolchain. If Northstar had to be half its conceptual size, what remains is:
the spine, one compact working-rules contract, the handoff/worker/PR loop, and
structural (not prose) validation.

## First-principles baseline

What must Northstar accomplish, per `docs/vision/001-northstar-delivery-vision.md`:
operators run complex agent-led projects where agents stay inside real
planning, produce evidenced outcomes, and need less thread babysitting.

The smallest system that plausibly delivers that:

1. **A docs spine convention** — `vision/`, `architecture/`, `contracts/`,
   `roadmaps/`, `logs/`, `triage/` with one authority chain and naming rules.
   (~10 short files of doctrine plus a copyable skeleton.)
2. **One working-rules contract** — ready-state, stop conditions, definition of
   done, refactor posture. One binding surface, one doctrine home.
3. **A dispatch boundary** — worker handoff file + worktree/branch isolation +
   PR + review-before-merge. This is the part plain AGENTS conventions do not
   give you and is Northstar's strongest original contribution.
4. **Structural validation** — files exist, links resolve, names match
   patterns. Nothing that asserts prose content.
5. **One installable skill** with a handful of modes (plan, adopt/normalize,
   orchestrate, review, recover).

Everything else in the current repo should justify itself against that
baseline. Much of it can; a substantial fraction cannot.

## Strengths — the case for the current shape

- **It actually runs.** 43 g02 milestones, 116 batch cards, 124 evidence logs,
  real PRs reviewed and merged under the protocol, across ~8 repositories.
  Few internal frameworks can show a chain like g02.042's log: oracle rows,
  adversarial review findings with reason codes, and honest limitations.
- **The authority chain solves a real LLM problem.** "Where does truth live,
  what may I infer, when must I stop" is exactly what agents get wrong, and
  the spine answers it without conversation history. Plain AGENTS.md
  conventions do not give you ready-state, evidence logs, or a dispatch
  boundary.
- **Honesty discipline is real.** Limitations sections admit missing dogfood;
  the architecture explicitly denies certification claims; consumer evidence
  is labeled operator-owned rather than inflated.
- **Contract 003 (agent instruction surface) is genuinely good** — portable,
  reasoned, budget-aware; arguably the most externally reusable single
  artifact in the repo.
- **Duplication is partly deliberate**: binding repo contracts vs doctrine is
  a coherent two-tier design, and the protocol kernel exists precisely to
  manage it. The failure is scale, not concept.

## Flaws and gaps (ranked by impact; confidence noted separately)

1. **Self-referential effort dominates.** 59% of doc mass and most of g02
   plan Northstar itself. The system's cost curve is set by its own protocol
   growth, not by user problems. *Impact: high. Confidence: high.*
2. **Prose-asserting validation is a standing tax.** Substring assertions on
   doctrine wording (positive and negative) mean truthful edits fail QA
   (PAPERCUTS 2026-08-16 ×2) and every protocol change must also edit checker
   data. The parallel-first change added 13 positive + 5 negative prose
   assertions for one behavioral default. This is checker self-consistency
   masquerading as evidence. *Impact: high. Confidence: high.*
3. **Change amplification.** One protocol decision touches contract + doctrine
   section + kernel + template contract + skill mode + SKILL.md + handoff
   contract + templates + operator docs + checker data (12 surfaces in
   g02.042). Enumerations duplicated across ≥14–15 files (ready-state,
   continuation envelope). The kernel's "single canonical home" rule is
   stated but not achieved. *Impact: high. Confidence: high.*
4. **Protocol features ship without executed proof.** Parallel-first dispatch
   merged with no live multi-worker run; capacity-discovery
   (refusal-as-capacity) and sibling-symlink semantics are specified in
   detail but exercised zero or one time. The repo's own doctrine ("manual
   evidence before automation", "completion based on evidence") is applied
   to consumer work more rigorously than to protocol work.
   *Impact: medium-high. Confidence: high.*
5. **No external consumer evidence.** Every adoption proof is the operator's
   own repos. The reusability claim, the operator docs, and the strict
   migration program (specs 012–019) are calibrated to one user. Either an
   external consumer is a real goal (then it needs a lane and radical
   simplification of onboarding) or Northstar should be honestly rescoped as
   a personal operating system, which would justify deleting significant
   generic-audience surface. *Impact: high. Confidence: high that the gap
   exists; low confidence on which resolution is right — operator decision.*
6. **Mission creep via language-quality packs.** Contract 004 + specs 031–033
   + 32 reference files + a Cargo-native binary + evidence harnesses is a
   second product embedded in the first. It also produced the most painful
   papercuts (frozen-cohort halts costing 467–589s each, false-green
   qualifiers). *Impact: high. Confidence: medium — the packs may be exactly
   what the operator wants; the cost accounting is the fact, the verdict is
   theirs.*
7. **Skill surface breadth.** 21 modes with overlapping intents contradicts
   the vision constraint "public skill surface should stay small". Router +
   mode + doctrine reads make simple tasks context-heavy.
   *Impact: medium. Confidence: high.*
8. **Template drift.** The copy-ready working-rules template and the live
   contract differ by 946 diff lines; adopters get a materially older
   grammar than the one Northstar actually runs. Either the delta is
   deliberate (then document the boundary) or it is drift.
   *Impact: medium. Confidence: medium.*
9. **Discovery-route schema weight.** Readiness maps and decision records
   impose stable-ID, frontmatter, and link-scope rules on what is
   fundamentally a structured conversation; one live map exists.
   *Impact: low-medium. Confidence: medium.*

## Over-engineering and coupling candidates

- `scripts/lib/northstar-repo-contract-data.rhai` (493 lines): 167 required
  paths (including individual historical batch cards), ~280 lines of
  `required_content` prose assertions, plus `forbidden_content` negative
  assertions. Retire the prose classes; keep existence/link/naming checks.
- Continuation envelope + lane budget + pause signal (specs 010/011, contract
  001): three named abstractions where "N cards / T minutes, stop on gaps,
  say why you stopped" covers observed behavior.
- Worker-start preflight enumeration (contract 001 lists ~13 dispatch
  conditions; architecture repeats them; mode repeats them; handoff template
  repeats them).
- Near-duplicate skill modes: reframe / refresh / recovery / refocus /
  replan / cleanup / readiness-review overlap heavily in reads and outcomes.
- `bundle-docs/` at 70 files/10.2k lines for doctrine that the kernel
  summarizes in 73 lines; sections 07 alone is 861 lines.

## Missing evidence

- Any measurement of the claimed payoff: babysitting time, correction rate,
  review-cycle counts before vs after protocol features (the README's own
  "Next task" — timing a fresh-user walkthrough — appears never to have run).
- Live multi-worker parallel dispatch (g02.042 limitation).
- A second planning-delegate run, second mechanical projection, second
  Paseo-lifecycle consumer.
- Everyday TypeScript authoring (failed its no-regression gate; explicitly
  unavailable — honest, but the catalogue investment predates the proof).
- Any non-operator adopter, or even a structured external usability read.

## Ranked recommendations

R1. **Freeze the orchestration-protocol growth curve.** Declare the current
protocol feature-complete for a measurement window; spend the next milestones
running it (live parallel dispatch, more delegate runs) and recording
outcome metrics instead of adding rules. *(High impact, high confidence.)*

R2. **Retire prose assertions from validation.** Keep file-existence, link,
naming, and parity checks; delete `required_content`/`forbidden_content`
substring classes and the per-historical-card required paths. Structured
front-door fields (as PAPERCUTS 2026-08-16 suggests) can replace the few
currentness checks worth keeping. *(High impact, high confidence.)*

R3. **Put the language-quality packs to an explicit operator decision:**
(a) split into a sibling product with its own repo/roadmap, (b) freeze at
current capability and stop investing, or (c) affirm mission expansion and
say so in the vision. Default recommendation: (a) or (b); the docs spine
should not inherit their maintenance tax. *(High impact, medium confidence.)*

R4. **Deduplicate enumerations for real.** One doctrine home per enumeration
+ pointers; compress contract 001 back toward a binding summary; reconcile or
deliberately version the template-bundle contract. *(Medium-high impact, high
confidence.)*

R5. **Consolidate the skill to ~8 modes** (plan, adopt/normalize, refresh
[absorbing recovery/cleanup/refocus/replan/reframe], readiness/atlas,
orchestrate, PR review, handoff, language-audit adapters if retained).
*(Medium impact, medium-high confidence.)*

R6. **Resolve the audience question.** Either commit to one external adopter
as a g02 goal (with a minimal-first onboarding path measured end-to-end) or
rescope as operator-personal and delete generic-audience surface. *(High
impact; the choice is the operator's.)*

R7. **Collapse the autonomy taxonomy** (envelope/budget/pause signals) into
the simple bounded-run rule unless a concrete incident shows the taxonomy
earning its weight. *(Medium impact, medium confidence.)*

## Alternatives considered

- **Do nothing / current shape is fine:** defensible short-term — everything
  passes QA and work is flowing. Rejected as steady state because the cost
  curve (change amplification, checker tax) compounds with every milestone.
- **Full rewrite to the minimal baseline:** rejected; the evidence chain and
  working protocol are real assets, and the handoff's non-goals exclude
  rewrite-from-scratch demands. Subtraction beats reconstruction here.
- **Keep prose checkers but auto-generate them from canonical docs:** viable
  middle path for R2, but it preserves the coupling; noted for the
  orchestrator if R2 is judged too aggressive.
